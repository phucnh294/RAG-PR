## CONTEXT THE NEXT SESSION CANNOT DERIVE FROM CODE

- **`rag-ai-local/template/` does not exist**, despite `CLAUDE.md` and `.claude/rules/file-organization.md` both referencing template files there (`session_handoff_template.md`, etc.) and the `write-handoff-doc`/`write-functionality-doc` skills instructing "copy the template." This doc (and the previous one, `09212026/01_...`) was hand-structured to match the frontmatter/section shape those rules describe, since there was nothing to literally copy. If a future session is asked to create these templates, that's new work, not a repair of something broken — the folder appears to have simply never been populated in this repo.
- **Why the store is split into `dummy_store` (fake) and `postgres_store` (real) instead of one implementation:** the user chose "full replace" when asked whether Postgres should be the single source of truth (see the previous handoff's session that preceded PR #5) — but requiring every unit test to talk to a live Postgres container would make the test suite slow and environment-dependent. The compromise: production code (routes, both pipeline orchestrators) only ever imports and calls `rag_backend.db.postgres_store`, never `dummy_store` directly. `backend/tests/conftest.py`'s autouse `_fake_postgres_store` fixture monkeypatches every public function on the `postgres_store` module object to point at the same-named function on `dummy_store` for the duration of each test. This means the exact same call sites run in both prod and test — only the implementation underneath differs. **If you add a new function to `postgres_store`, you must add a same-named, same-signature function to `dummy_store` too, and add its name to the `_STORE_FUNCTIONS` tuple in `conftest.py`**, or tests calling that new function will hit a real (uninitialized) connection pool and raise `RuntimeError: Postgres connection pool is not initialized`.
- **The `steps` JSON structure is a breaking rename, not an addition.** The very first version of pipeline logging (from earlier in this same session, since superseded) used a flat `step_timings_ms: {step_name: float}` field. That field **no longer exists** — it was fully replaced by `steps: {step_name: {duration_ms: float, output: dict}}` in commit `0270caf`. If anything outside this repo (a dashboard, a script) was written against the old shape, it needs updating. Within the repo, the only consumers are the tests (already updated) and the `LogsPage.tsx` UI (which just dumps the whole `record` as pretty-printed JSON, so it needed no change).
- **Why indexing pipeline logging was added even though the user's literal request ("log in every step... system prompt, user chat, return log") only describes retrieval:** an earlier turn in this session asked "should this cover both pipelines?" via `AskUserQuestion`, and the user picked "both." So indexing's per-step output logging is deliberate, confirmed scope — not scope creep.
- **The reused doc-corpus schema decision from the previous handoff still stands and is load-bearing.** `rag_documents`/`rag_chunks`/`rag_embeddings` were originally designed (per the user's own hand-edit to `postgres/init/01-create-extension.sql`) for embedding this repo's own knowledge docs, not app uploads. The user explicitly confirmed reusing the same generic columns for uploaded files (`source_path` = `data/input/<id>/<filename>`, `title` = original filename, `doc_type` = mime type, `metadata` jsonb carries `content_hash`/`size_bytes`/`excerpts`/`error_message` since there are no dedicated columns for those). Don't "clean this up" into dedicated columns without re-confirming — it was a deliberate, discussed tradeoff, not an oversight.
- **Every backend or frontend code change in this session required an explicit `docker compose up -d --build <service>` before it took effect in the running containers** — there is no live-reload/hot-mount wired into `docker-compose.yml` for either service. Forgetting the rebuild step and testing against a stale container was a repeated near-miss pattern this session (caught each time by checking `docker compose ps` uptime and re-grepping the served bundle for new symbols) — keep doing that check rather than assuming a code edit is live.
